This is the bug in Demo 03 and the saved output in Demo 01. The point is not that the model is bad at C++. Avoid presenting the model as an autonomous engineer. Its value grows when we provide persistent context, constrain the task, and verify the result with the same engineering system used by the team.

Adoption levels

Where are we on the adoption ladder?

1 · PromptingAnswerYou ask, you judge every reply.
2 · Assisted codingEditThe model prepares a bounded code change.
3 · Agentic codingTaskThe agent runs a whole engineering task.
4 · Spec-drivenContractThe agent implements a specification with acceptance criteria.
5 · Bounded autonomyProcessThe agent runs part of a recurring process within guardrails.

The level is per process: bounded autonomy for test generation can sit next to assisted coding for security-sensitive changes.

Skip this slide if time is short. It is a workshop model, not an industry standard. Maturity comes from a repeatable process, a controlled decision scope, and evidence, not from buying access to a model. Ask each person which level their last real task was at.

Prompt audit

/claude-api prompt-audit

Repository instructions hold durable rules; skills hold repeatable procedures. /claude-api prompt-audit CLAUDE.md returns a report and a proposed diff and does not edit files. It flags capitalized emphasis, step-by-step scaffolding, stale paths and commands, and contradicting instructions. Check each finding against the real build commands and platform constraints before accepting it. A clean audit is a valid result.

These are the prompts from Demo 04, shortened. The vague prompt leaves the model to invent scope and style. The contract names the files, the language and compiler limits, what is out of scope, and how to verify. Run both live and compare the diffs, not the summaries.

Reading local files costs no remote calls, and only local source can be compiled and tested. Model routing

Match the model to the step

01 · TicketYouCriteria and scope
02 · PlanOpusSpec and risks, low or medium effort
03 · BuildSonnetImplement the approved spec, medium effort
04 · VerifyBuild and testsEvidence per target
05 · ReviewOpusAdversarial review, high effort
Opus 5.5 lists at $4 input and $20 output per million tokens; Sonnet 5.5 at $2 and $10, so half per token. Sonnet 5.5 is positioned for well-scoped everyday coding, which is what an approved spec is. No source we found measures Opus against Sonnet on the same task, so treat savings as unproven and have the team run one ticket both ways. In Claude Code: /model opusplan uses Opus in plan mode and Sonnet in execution, or set model in a skill's frontmatter as Demo 07 does. Escalate to Opus when Sonnet fails the same problem three times. Details and sources: MODEL-ROUTING.md.

Three hooks in the demo

A rule in CLAUDE.md asks; a hook enforces. The messages on the right are the real output of the Demo 06 scripts, with the long file path shortened. A hook is a command that runs with your permissions, so review it like any other script before enabling it. Hooks and CI cover what must always run; skills cover procedures needed only sometimes.

Safety

Text from outside is data, not instructions

01 · Untrusted textIssue, PR comment, log, web pageAnyone can write into it.
02 · Agent readsData, not ordersA hidden "run this command" is content to report.
03 · Permission gateAsk before actingLeast privilege for shell, network, and write tools.
04 · Hook and humanBlock, then reviewGuard hooks stop destructive commands; people approve PRs.
Skip this slide if time is short. It matters once GitHub MCP is in use, because issue and pull request text comes from people who may not be on your team. The defenses are layered: treat tool output as data, keep permissions narrow, add hooks for commands that must never run, and keep a person on writes such as opening or merging a PR.

Evidence contract

Every success claim needs observable proof

Claim

State exactly what now works.

Command

Record the reproducible check.

Observation

Capture output, artifact, or behavior.

Boundary

Name what remains unverified.

Keep proof boundaries honest. Local tests, CI, review, deployment, and live behavior are distinct. A successful build proves compilation. It does not prove production behavior.
